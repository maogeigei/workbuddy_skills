# multi-session-collab

让一个主会话带着一群子会话干同一个活，不至于互相打架、互相等、或者假装干完了。

说具体点：主会话负责判断和派活，协作会话一线一棒、干完就退，脚本负责记台账、算缺口、报异常、维护看板。用户只看一个看板。

这套东西是在 WorkBuddy 桌面版上真跑出来的，跑了两天两夜，被推翻过三轮，踩的坑都留在 `references/pitfalls.md` 里。文档里的"当前结论"就是这么来的，不是设计出来的。

---

## 一、它治什么

多会话协作听着简单，真跑起来会出一种最费时间的错：**看起来一直在动，工期就是不动**。具体长这几种样子。

**大家互相等。** 每个会话都在等上游给东西，上游又在等下游确认，一天下来谁都没往前推一步。

**链条从中间断开。** 第三棒干完，负责派第四棒的那个环节没了。没人发现，一直到第二天用户发消息，才有人接上。

**把排期当成成果。** 日志里写满"下一棒已派"，看着热闹，实际真做完的件一个没有。

**两个会话改同一份文件。** 一个在改脚本，另一个也在改，后写的盖掉先写的，两边都不知道。

**为了盯进度，又开一个会话。** 于是多了一个需要被盯的会话。

## 二、骨架

```
            用户
             │  提需求 · 看板 · 放行
             ▼
           主会话 ─────────────────────────────┐
             │ ① 派活（写一行排期）             │ ④ 收结果（直读宿主库）
             ▼                                 │
      协作会话（一线一棒，一次一件）           │
             │ ② 上报                           │
             ▼                                 │
      协作程序 ──── 队列 ────▶ 投递 ───────────┘
    （台账 · 判定 · 看板）      （③ 通知主会话）
             ▲
             └── 宿主 WorkBuddy：状态 · 调度 · 事件 · 锁
```

四个主体各管一摊，谁也不越界：

| 谁 | 只做 | 不做 |
|---|---|---|
| 用户 | 定目标、改方向、做决策。看板、放行、喊停归你 | 不管过程，也不用催进度 |
| 主会话 | 判断加派活：读库和看板判缺口，写一行排期 | 不替别的线干活，不做机械核对 |
| 协作会话 | 一棒一线，一次一件。干完写产物，顺手判本线缺口接下一棒 | 不跨线，不夹带，不常驻 |
| 协作程序 | 持有台账，收上报，判定、告警、体检、看板覆写 | 不派活，不推进队列 |

宿主（WorkBuddy 本身）是地基，提供四样：状态、调度、事件、互斥。它不算主体。

## 三、四条通道

这套设计里最值钱的一张表。哪件事走哪条路，走错就是最大的一笔浪费。

| 要干的事 | 走哪条路 | 代价 |
|---|---|---|
| 派活、开新会话 | 宿主的自动化排期 | 一个会话 |
| 收结果、检测 | 直读宿主数据库 | 零 token，不轮询不扫文件 |
| 通知主会话 | 钩子唤起脚本跑一轮 | 零 token，零会话，零常驻 |
| 机械判断（文件在不在、返回码、端口通不通） | 本地脚本 | 零 token，几毫秒的事 |
| 人看进度 | 一个看板 | 就这一处 |

两个最容易搞混的地方。

**"发消息给另一个会话"和"读它的结果"是两件事。** 前者要走网关投递，后者读一下数据库就行。我刚做的时候把两件事混成一件，白花了不少力气。

**"我需要持续监控"不等于"要开一个自动化"。** 第一反应应该是让钩子按需唤起本地脚本。钩子是宿主起的子进程，天生带着网关口令，不占会话，跑完就退。

后面这条认知来得不便宜。我一度把"投递要有口令"推成"必须有常驻进程"，用户当场回了一句"又给我整到自动任务去了"。真因是我把可选手段当成了唯一手段。

## 四、几条硬规矩

### 任务图和关键路径

`任务图.json` 里每个节点写清 id、标题、线、依赖、状态、证据。四条派活规则写进文件的 `rules` 字段，程序和人照同一份执行：

1. 只派依赖已满足的节点，能并行的立刻并行
2. 优先关键路径上的节点，非关键路径押后不拖工期
3. 一条线同时只挂一件，多条线可以同时挂
4. 收口就派，别留 5 到 8 分钟的空窗

判断有没有浪费，看两个信号：可派集合非空但没有任何棒在跑，说明有活没人干；关键路径上只剩一个执行主体，那就得把它拆小，能交出去的部分并行出去。

### 证据分级

不区分这个，就会被空转的链条骗。

| 类别 | 判据 | 算进展吗 |
|---|---|---|
| 真成果 | 有运行记录、有结论，最好有能核对的产物或读数 | 算 |
| 接续任务 | 只是又排了下一棒 | 不算 |
| 刚开始跑 | 有记录，还没结论 | 不算 |
| 哑火 | 到点了没有任何运行记录 | 当异常处理 |

"在跑的棒有 N 个"是排期数，不是成果数。这句话得写进汇报口径里，否则进度会长期虚高。

### 严格队列

队列管"谁做下一件"，域锁管"能不能动这个资源"，两个都要。

一次只放一个队首。取件靠 `mkdir` 的原子性：建成了就是你取到，建不成说明别人拿走了，换队首或等。做完必须删掉 claim，下一个才可能上队首，不删的话这条线就一直被占着。同一条线同时只允许一件，不同线按 `line` 并行。

claim 超过 20 分钟没续期，程序自动把它挪去 `claims-stale/`，可追溯，不删。

优先级判据有个坑：得看节点是不是落在**关键路径的上游闭包**里，而不是只看它本身在不在关键路径上。只看本身会漏掉它的前置，实测出现过队首推荐了一个跟关键路径无关的节点。

### 域锁按文件切

域锁按节点涉及的文件或子目录声明，不按工作区、不按 cwd。

把整个工作区声明成一个域，等于自己造了个串行瓶颈。实测好几次"抢锁失败，整轮白开"的纯浪费。反过来，两个会话各报自己的 domain，域不重叠就是真并行。

还有个更基本的问题：域锁定义了不等于生效，得有人真的去抢。派活的模板里必须带上"开工第 0 步先抢域锁"，漏了这句等于没接这条线。

### 新建自动化要过白名单

只有两类可以不问用户直接建：接续会话（把某条链的下一棒接上）、给别的会话派活。

其余用途——巡检、体检、日报、清理、监控——先问。配额是每条需求线不超过 2 个，一个心跳加一个截止类就够了。

这条规矩是被逼出来的。曾经一个需求挂上 7 个自动化，其中 5 个用途重复。

### 看板不能影响主流程

看板是只读旁路。后台线程定时产快照，请求线程只读内存里的缓存，不碰数据库、不读文件。开几个标签页都不给主流程加负担。

数据取不到时，顶部显示黄条说明哪一块没读到，不伪装成"0 个会话"。刷新失败就保留上一份快照，界面上写"数据延迟 N 秒"。看板报假数是比看不到更坏的事。

## 六、装起来

```
① 把技能目录放到 <配置目录>/skills/multi-session-collab/
② 复制配置并改 4 个必填项
     cp scripts/collabd.config.example.json scripts/collabd.config.json
     改 workspace / inbox / live / taskgraph
③ 接钩子。让宿主在这两个事件上调用本地脚本：
     UserPromptSubmit
     PreToolUse（匹配 ^Bash$）
   脚本内部做两件事，都节流、都无窗口：
     collabd.py --once    投影一轮，不投递
     collabd.py --tick    投递一轮，同时推进队列
```

第三步就是投递的全部。不需要排期，不需要常驻进程。

新加的钩子事件要宿主完全重启后才生效。钩子只能指向一份脚本，同目录留了旧副本，就会出现代码在 A、钩子在 B 的情况，表现为改什么都不生效。

**验收，逐条能测：**

1. `collabd.py --where` 打印的三个路径都对
2. `collabd.py --once` 返回 0，产出台账和机械摘要，没有异常栈
3. 造一条上报：`--report T1 --state running --line <线> --by <会话名>`，然后 `--reqs` 能看到它
4. `collabd.py --tick` 返回 0。注意投递成功的判据不是返回 0，而是 `wakeups.jsonl` 新增了一行 `ok:true`
5. `collabd.py --declare --role main` 能声明会话角色
6. `python scripts/selftest.py` 全绿

## 七、这份开源版做过什么脱敏

代码是从作者本机正在跑的那一份导出来的，功能没动，改动只有一类：去掉只对作者那台机器有意义的东西。

**删掉的**

- 写死的本机绝对路径。配置目录的回退值原来是具体盘符，现在回退到 `~/.workbuddy`
- 内网域名、私有项目名、服务器地址。文档里的例子换成 `<业务线A>`、`示例主题` 这类占位
- 一段业务专属的前置探测（去探两个业务进程的端口和日志）。它本来就不属于这套机制，部署手册里自己也写着"本机制不含业务专属项"
- 一节业务链路的部署说明，里面全是私有域名、路径和启动命令

**改了名字的环境变量**

| 原来 | 现在 |
|---|---|
| `DSH_COLLAB_WS` | `COLLABD_WS` |
| `DSH_GUARDED` | `COLLABD_GUARDED` |

**需要你自己配的**

| 环境变量 | 作用 | 不配会怎样 |
|---|---|---|
| `COLLABD_CONFIG` | 配置文件路径 | 转去找 `<工作区>/.workbuddy/collab/collabd.config.json`，都找不到就拒绝启动 |
| `COLLABD_WS` | 工作区路径 | 回落到当前目录 |
| `COLLABD_HOOK_PATH` | 钩子脚本路径 | 自测跳过"钩子里确实调了 `--tick`"这条检查 |
| `COLLABD_LEAK_PAT` | 你自己项目的专属串（正则） | 自测只做结构性检查，不查项目串泄漏 |
| `COLLABD_STALE_KEYS` | 你已废弃的看板键名，用 `|` 分隔 | 同上，这条跳过 |

脱敏之后跑了一遍回归自测，26 条用例全绿（`python scripts/selftest.py`）。

## 八、已知边界

写在这里，免得照着文档再踩一遍。

**全员静止时不会有通知。** 投递靠宿主钩子触发，钩子要有会话活动才会响。所有会话都闲着、WorkBuddy 也退出了，通知就发不出去，得等下一次有人干活再补投。要真正的心跳时钟，得另外准备一条会话外的常驻，这是设计上明确接受的代价，不是忘做了。

**并发上报可能丢一条。** `--report` 读写台账时没有加锁。两条上报精确同时发生，后写的会盖掉前者。概率不高，上报是毫秒级写小文件，棒之间一般撞不上。绕法是上报后回读核对一遍。真正的写锁改造试过一次，导致 `--once` 和 `--report` 全部卡死超时，已经从备份回退。要做这个改造，得先在隔离环境里验证锁的行为，别在用户在等的时候赶工。

**两份同名副本是最难查的故障。** 工作区里留着旧副本、钩子又指向旧副本，改新代码完全不生效，而且一切看起来都正常。

**文档之间还有互相矛盾的地方。** 这几份文档是从真实会话里长出来的，架构改过三轮（常驻、按需唤起、再回退），旧结论一律就地标注而不是删掉，所以读的时候要认每份文档开头的「当前结论」那一节。目前 `SKILL.md` 和 `references/architecture.md` 对"投递算不算独立主体"的口径还不一致，前者说已退役，后者还把它列为第 5 个主体。

**宿主是硬依赖。** 钩子和宿主数据库是这套机制的地基，离开 WorkBuddy 跑不起来。
