# multi-session-collab

一个 WorkBuddy 技能：一个主会话带着一群子会话干同一个活。

分工是固定的。主会话管判断和派活：读一眼台账和看板，判出哪步真完成了、下一个该派谁，然后写一行排期。协作会话领一件活，干完就退，顺手判断本条线还有没有缺口。剩下的脏活全给本地脚本，记账、核对产物、发现异常、维护看板，一样都不花 token。你要做的只是看一个看板。

这套东西在我本机真跑过两天，中间架构改过三轮，每轮为什么改、后来为什么又改回来，文档里都留着。所以这份 README 除了讲设计，还会讲哪些地方翻过车。

## 一、它解决什么

多会话协作最常见的失败不是吵架，是空转：每个会话都有产出，日志看着热闹，总工期一格没动。

几种典型的样子。大家互相等，A 等上游给东西，上游在等下游确认，一天下来没人往前走。链条从中间断开，某一棒干完了，负责接下一棒的环节没了，没人发现，因为负责报警的程序自己也停了，直到第二天有人发消息才接上。更隐蔽的一种是把"已经排了下一棒"当成"这步干成了"，日志里全是"已派"，真做完的件一个没有，进度汇报长期虚高。剩下两类是物理冲突：两个会话同时改一份文件，后写的盖掉先写的；为了盯进度再开一个会话，从此多了一个需要被盯的会话。

这个技能就是冲着这些来的。后面每条规矩背后都有一次真实的翻车，踩坑清单在 references/pitfalls.md，二十来条，每条都真发生过。

## 二、骨架

![协作看板](assets/board-screenshot.png)

这张图就是看板本身，也是整套机制的地图。顶上一条是当前目标和验收判据，每项验收过没过直接列着。中间从上往下：用户在最上面，主会话接需求、派活；然后是按线分的分工板块，一条线一格，显示最近干完的件、现在谁在做、还剩几件没完；再往下是协作程序和它的上报、Hook 进程；最底下一条是宿主 WorkBuddy，整套机制跑在它上面。

四个角色的分工是死的，谁也不越界：

| 谁 | 只做 | 不做 |
|---|---|---|
| 你 | 定目标、改方向、做决策；看板、放行、喊停 | 不管过程，不用催进度 |
| 主会话 | 判断加派活：读库和看板判缺口，写一行排期 | 不替别的线干活，不做机械核对 |
| 协作会话 | 一棒一线，一次一件；干完写产物，顺手判本线缺口接下一棒 | 不跨线，不夹带，不常驻 |
| 协作程序 | 持有台账，收上报，判定、告警、体检、看板覆写 | 不派活，不推进队列 |

宿主（WorkBuddy 本身）是地基，出四样东西：状态、调度、事件、互斥。它不算角色。

## 三、四条通道

整套机制围着一张表转：每件事只有一条路可走，走错就是白花钱。

| 要干的事 | 走哪条路 | 代价 |
|---|---|---|
| 派活、开新会话 | 宿主的自动化排期 | 一个会话 |
| 收结果、检测 | 直读宿主数据库 | 零 token，不轮询不扫文件 |
| 通知主会话 | 钩子唤起脚本跑一轮 | 零 token，零会话，零常驻 |
| 机械判断（文件在不在、返回码、端口通不通） | 本地脚本 | 零 token，几毫秒的事 |
| 人看进度 | 一个看板 | 就这一处 |

有两个地方容易搞混，我都栽过。

"发消息给另一个会话"和"读它的结果"是两件事。前者要走网关投递，后者读一下数据库就行。我一开始混成一件，绕了半天。

第二条代价更大。我一度把"投递要有口令"推成"必须有常驻进程"，被一句「又给我整到自动任务去了」当场点破。错在我把可选手段当成了唯一手段：钩子也是宿主起的子进程，一样有口令，还不占会话，跑完就退。

## 四、几条硬规矩

### 任务图和关键路径

`任务图.json` 里每个节点写清 id、标题、线、依赖、状态、证据。四条派活规则写进文件的 rules 字段，程序和人照同一份执行：只派依赖已满足的节点，能并行的立刻并行；优先关键路径上的节点，非关键路径押后不拖工期；一条线同时只挂一件，多条线可以同时挂；收口就派，别留 5 到 8 分钟的空窗。

判断有没有浪费，看两个信号：可派的活没人干，说明有活没人接；关键路径上只剩一个执行者，那就得把它拆小，能交出去的部分并行出去。

### 证据分级

这条不立规矩，进度汇报最先出问题。

| 类别 | 判据 | 算进展吗 |
|---|---|---|
| 真成果 | 有运行记录、有结论，最好有能核对的产物或读数 | 算 |
| 接续任务 | 只是又排了下一棒 | 不算 |
| 刚开始跑 | 有记录，还没结论 | 不算 |
| 哑火 | 到点了没有任何运行记录 | 当异常处理 |

汇报时记住一条：在跑的棒有几个，是排期数，不是成果数。混了这两样，进度就长期虚高。

### 严格队列

队列管"谁做下一件"，域锁管"能不能动这个资源"，两个都要。

一次只放一个队首。取件靠 mkdir 的原子性：建成了就是你取到，建不成说明别人拿走了，换队首或等。做完必须删掉 claim，下一个才可能上队首，不删的话这条线就一直被占着。同一条线同时只允许一件，不同线按 line 并行。claim 超过 20 分钟没续期，程序自动挪去 claims-stale/，可追溯，不删。

优先级有个坑：得看节点是不是落在关键路径的上游闭包里，不能只看它本身在不在关键路径上。只看本身会漏掉它的前置，实测出现过队首推荐了一个跟关键路径无关的节点。

### 域锁按文件切

域锁按节点涉及的文件或子目录声明，不按工作区、不按 cwd。

把整个工作区声明成一个域，等于自己造了个串行瓶颈，实测好几次"抢锁失败，整轮白开"。反过来，两个会话各报自己的 domain，域不重叠就是真并行。

还有个更基本的问题：域锁定义了不等于生效，得有人真的去抢。派活的模板里必须带上"开工第 0 步先抢域锁"，漏了这句等于没接这条线。

### 新建自动化要过白名单

只有两类可以不问直接建：接续会话（把某条链的下一棒接上）、给别的会话派活。其余用途，巡检、体检、日报、清理，先问。配额是每条需求线不超过 2 个。

这条规矩是被逼出来的：曾经一个需求挂上 7 个自动化，其中 5 个用途重复。

### 看板不能影响主流程

看板是只读旁路。后台线程定时产快照，请求线程只读内存里的缓存，不碰数据库、不读文件，开几个标签页都不给主流程加负担。

数据取不到就显示取不到，写明是哪一块；刷新失败就保留上一份快照，界面上写"数据延迟 N 秒"。装作"0 个会话"，看的人会被带偏。

## 六、装起来

```
① 把技能目录放到 <配置目录>/skills/multi-session-collab/
② 复制配置并改 4 个必填项
     cp scripts/collabd.config.example.json scripts/collabd.config.json
     改 workspace / inbox / live / taskgraph
③ 接钩子。让宿主在这两个事件上调用本地脚本：
     UserPromptSubmit
     PreToolUse（匹配 ^Bash$）
   脚本内部做两件事，都节流、都无窗口：
     collabd.py --once    投影一轮，不投递
     collabd.py --tick    投递一轮，同时推进队列
```

第三步就是投递的全部，不需要排期，也不需要常驻进程。

新加的钩子事件要宿主完全重启后才生效。钩子只能指向一份脚本，同目录留了旧副本，就会出现代码在 A、钩子在 B 的情况，表现为改什么都不生效。

验收，逐条能测：

1. `collabd.py --where` 打印的三个路径都对
2. `collabd.py --once` 返回 0，产出台账和机械摘要，没有异常栈
3. 造一条上报：`--report T1 --state running --line <线> --by <会话名>`，然后 `--reqs` 能看到它
4. `collabd.py --tick` 返回 0。注意投递成功的判据是 `wakeups.jsonl` 新增一行 `ok:true`，返回 0 说明不了什么
5. `collabd.py --declare --role main` 能声明会话角色
6. `python scripts/selftest.py` 全绿

## 七、这份开源版做过什么脱敏

代码是从我本机正在跑的那一份导出来的，功能没动，改动只有一类：去掉只对我这台机器有意义的东西。

删掉的：

- 写死的本机绝对路径。配置目录的回退值原来是具体盘符，现在回退到 `~/.workbuddy`
- 内网域名、私有项目名、服务器地址。文档里的例子换成 `<业务线A>`、`示例主题` 这类占位
- 一段业务专属的前置探测（去探两个业务进程的端口和日志）。它本来就不属于这套机制，部署手册里自己也写着"本机制不含业务专属项"
- 一节业务链路的部署说明，里面全是私有域名、路径和启动命令

改了名字的环境变量：

| 原来 | 现在 |
|---|---|
| `DSH_COLLAB_WS` | `COLLABD_WS` |
| `DSH_GUARDED` | `COLLABD_GUARDED` |

需要你自己配的：

| 环境变量 | 作用 | 不配会怎样 |
|---|---|---|
| `COLLABD_CONFIG` | 配置文件路径 | 转去找 `<工作区>/.workbuddy/collab/collabd.config.json`，都找不到就拒绝启动 |
| `COLLABD_WS` | 工作区路径 | 回落到当前目录 |
| `COLLABD_HOOK_PATH` | 钩子脚本路径 | 自测跳过"钩子里确实调了 `--tick`"这条检查 |
| `COLLABD_LEAK_PAT` | 你自己项目的专属串（正则） | 自测只做结构性检查，不查项目串泄漏 |
| `COLLABD_STALE_KEYS` | 你已废弃的看板键名，用 `|` 分隔 | 同上，这条跳过 |

脱敏之后跑了一遍回归自测，26 条用例全绿（`python scripts/selftest.py`）。

## 八、已知边界

几个要如实交代的限制，免得照着文档再踩一遍。

投递靠宿主钩子触发，钩子要有会话活动才会响。全员都闲着、WorkBuddy 也退出的时候，通知发不出去，要等下一次有人干活再补投。要真正的心跳时钟，得另外准备一条会话外的常驻，这是设计上接受的代价，不是忘做了。

`--report` 读写台账没加锁，两条上报要是精确撞在同一毫秒，后写的会盖掉前者。概率不高（毫秒级写小文件，两个棒一般撞不上），绕法是上报后回读核对一遍。真要加锁得慎重：我试过一次，`--once` 和 `--report` 全部卡死超时，只能从备份回退。要做这个改造，先在隔离环境验证锁的行为，别在有人等着的时候赶工。

最难查的一种故障是同名旧副本：工作区里留着旧代码，钩子又指向它，改新代码完全不生效，而一切看起来都正常。

文档是从真实会话里长出来的，架构改过三轮，旧结论就地标注没有删，读的时候认每份文档开头的「当前结论」一节。还有一个没收拾干净的：SKILL.md 和 architecture.md 对"投递算不算独立主体"的口径不一致，一个说已退役，一个还把它列为第 5 个主体。

最后，宿主是硬依赖。钩子和宿主数据库是这套机制的地基，离开 WorkBuddy 跑不起来。
